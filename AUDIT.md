# Code Audit

| # | File | Location | Severity | Category | Description | Correct Fix |
|---|------|----------|----------|----------|-------------|-------------|
| 1 | `route.ts` | POST, `db.execute(...)` | Critical | Security | **SQL injection** — `notes` is free-text user input interpolated directly into a raw SQL string: `` `VALUES ('${runId}', '${parsed.notes ?? ''}', NOW())` ``. An attacker can terminate the string and inject arbitrary SQL. | Replace with a Drizzle parameterized insert: `db.insert(reconciliationRuns).values({ id: runId, notes: parsed.notes ?? '', createdAt: new Date() })` |
| 2 | `route.ts` | GET, `db.execute(...)` | Critical | Security | **SQL injection** — `id` comes directly from `searchParams.get('id')` with no sanitization: `` `WHERE id = '${id}'` ``. Any value from the query string is interpolated raw. | Replace with `db.select().from(reconciliations).where(eq(reconciliations.id, id))` |
| 3 | `route.ts` | POST catch block | Critical | Security / Compliance | **Internal error details exposed** — `error.stack` is returned to the caller in the 500 response. Stack traces expose file paths, line numbers, and library internals. In a PCI DSS L1 environment this is a compliance violation (Requirement 6.4). | Return a generic message: `{ error: 'Internal server error' }`. Log the full stack server-side only. |
| 4 | `route.ts` | POST and GET handlers | Critical | Security | **No authentication** — neither handler checks for a valid session. Any unauthenticated caller can trigger a reconciliation run or read all reconciliation data. | Add `const session = await getSession(); if (!session) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })` at the top of both handlers. |
| 5 | `reconciler.ts` | `findMatch` | High | Logic | **Match by amount only** — two payments with the same dollar value will false-match. In a real payment portfolio (e.g. 500 SaaS subscriptions at $99/month) every record would match the wrong payment. | Match primarily by `payment.externalRef === bankRecord.reference`, with amount as a confirmation. Only fall back to amount-only if no reference match exists. |
| 6 | `reconciler.ts` | `reconcilePayments`, totals reduction | High | Logic | **Floating-point accumulation** — `bankData.reduce((sum, r) => sum + r.amount, 0)` performs IEEE 754 addition on dollar values. Across hundreds of records this produces a `difference` that is off by fractions of a cent, making the reconciliation report unreliable. | Convert amounts to integer cents on ingestion (`Math.round(amount * 100)`), perform all arithmetic in cents, and divide by 100 only for display. |
| 7 | `reconciler.ts` | `reconcilePayments`, `discrepancies` array | High | Logic | **Discrepancies never populated** — `discrepancies` is declared and returned but nothing is ever pushed into it. The loop finds matches but never checks whether amounts agree. Every reconciliation run returns `discrepancies: []` regardless of actual mismatches. | Inside the match branch, check `if (match.amount !== bankRecord.amount)` (or cent equivalents) and push `{ bankRecord, payment: match, amountDelta: calculateDelta(bankRecord.amount, match.amount) }` to `discrepancies`. |
| 8 | `reconciler.ts` | `reconcilePayments`, `totalBankAmount` | High | Logic | **Summary includes out-of-period bank records** — `totalBankAmount` is computed from all of `bankData` before the period filter is applied, but records that fail `isInPeriod` are skipped during matching. The summary total is inflated by records that were never considered for matching. | Compute `totalBankAmount` only from bank records that passed the `isInPeriod` check, not from the raw `bankData` array. |
| 9 | `reconciler.ts` | `reconcilePayments` | High | Logic | **No concurrency safety** — two simultaneous POST requests for the same period will both execute the same `SELECT` against `payments`, both find the same unmatched candidates, and both call `markReconciled` on the same payment IDs. This produces duplicate matched pairs and double-reconciliation. | Wrap the reconciliation logic in a database transaction with a row-level lock (`SELECT ... FOR UPDATE` on the payments being matched), or use an idempotency key on the `reconciliations` table with a unique constraint on `(periodStart, periodEnd)`. |
| 10 | `route.ts` | POST, `db.execute(...)` | High | Logic | **Duplicate reconciliation record** — the route manually inserts a row into `reconciliation_runs`, then `reconcilePayments()` inserts a separate row into `reconciliations`. One reconciliation run creates two records in two different tables with different IDs. The `runId` returned to the caller does not match the `id` returned by the reconciler. | Remove the manual `db.execute` insert from the route entirely. Let `reconcilePayments` own persistence and return its own generated ID. |
| 11 | `route.ts` | GET handler | High | API | **GET never returns a list** — the dashboard fetches `/api/v1/reconcile` with no `id` param, expecting `{ runs: [...] }`. But the GET handler does `WHERE id = '${id}'` with `id = null`, which always queries `WHERE id = 'null'` and returns an empty result. The dashboard will always be blank. | Add a separate list branch: if no `id` param, return all recent reconciliation runs with `db.select().from(reconciliations).orderBy(desc(reconciliations.createdAt)).limit(50)` wrapped as `{ runs: [...] }`. |
| 12 | `reconciler.ts` | `markReconciled` | Medium | Logic | **Only `pending` payments can be reconciled** — the status guard `payment.status === 'pending'` silently skips `cleared` payments. A payment that has been cleared by the bank but not yet reconciled is a normal, expected state. These payments will never be marked reconciled, permanently inflating `systemOnly`. | Change the guard to accept both: `if (payment && (payment.status === 'pending' \|\| payment.status === 'cleared'))`. |
| 13 | `reconciler.ts` | `parseBankDate` | Medium | Logic | **Timezone-naive date parsing** — `new Date("2026-01-15T14:30:00")` without a timezone suffix is parsed as **local time** in Node.js, not UTC. On a server in a non-UTC timezone, this shifts every bank date, causing period boundary misclassification. | Normalise bank date strings before parsing: if the string has no offset, append `Z` to force UTC interpretation: `new Date(isoString.endsWith('Z') \|\| /[+-]\d{2}:\d{2}$/.test(isoString) ? isoString : isoString + 'Z')`. |
| 14 | `route.ts` | POST catch block | Medium | API | **Zod validation errors return 500** — `ReconcileRequestSchema.parse(body)` throws a `ZodError` on invalid input, which is caught by the generic catch and returns a 500 with a stack trace. A malformed request is a client error, not a server error. | Catch `ZodError` separately before the generic catch and return `{ error: 'Invalid request', details: e.errors }` with status 400. |
| 15 | `dashboard.tsx` | `useEffect`, `setInterval` | Medium | Performance | **Interval never cleared** — `setInterval` is started but `clearInterval` is never called in the `useEffect` cleanup function. The interval fires every 3 seconds indefinitely, even after the component unmounts, causing a memory leak and potential state updates on an unmounted component. | Return a cleanup function: `const id = setInterval(...); return () => clearInterval(id)`. |
| 16 | `dashboard.tsx` | `useEffect` | Medium | Logic | **No initial data fetch** — `useEffect` only sets up a polling interval. The first data load is delayed 3 seconds after mount. The table will be empty on first render until the interval fires. | Call the fetch function immediately before setting up the interval, or use a `fetchRuns` helper called both directly and inside `setInterval`. |
| 17 | `reconciler.ts` | `markReconciled` | Low | Performance | **N+1 queries** — for each matched payment, `markReconciled` issues a `SELECT` followed by an `UPDATE`, two round-trips per match. With 200 matched payments that is 400 sequential DB calls inside the reconciliation loop. | Collect all matched payment IDs, then issue a single batched `UPDATE payments SET status = 'reconciled' WHERE id = ANY($1) AND status IN ('pending', 'cleared')` after the loop. |
| 18 | `route.ts` | POST response | Low | API | **Wrong HTTP status for resource creation** — the POST handler returns status 200. Creating a new resource should return 201 Created per HTTP semantics. | Change `{ status: 200 }` to `{ status: 201 }`. |
